Release versioning is calendar-based (Year.Month.Patch). Around two base releases are planned per year, with optional patch releases. The best-effort community support is roughly six months, and commercial support is available from multiple vendors. Please update regularly as explained in the upgrading and extending section to benefit from security and performance improvements.

Highlight features 26.10

  • Helm charts (experimental): The charts provide a 1:1 equivalent of the Kustomize manifests, with full Helm installation and end-to-end integration tests.

  • Kubernetes Versions: We have support for versions 1.35-1.37.0 as validated via CI/CD.
  • Kubeflow Workspaces 2.0.0 (Notebooks v2) as the new major release is now enabled by default, with Workspaces entries in the Central Dashboard. Notebooks v1 remains optional and is scheduled for removal in Kubeflow 27.03.
  • Kubeflow Notebooks v1.11.1 fixes the infinite status reconciliation loop in the notebook controller, improving scalability for existing Notebooks v1 installations.
  • Kubeflow Dashboard 2.0.1 includes many dependency and security updates, navigation fixes and self-service viewer management. See the Dashboard release notes.
  • Kubeflow Pipelines 2.18.0, with matching python packages. The version 1 SDK compatibility tests are retained, note however that KFP v1 support is scheduled for removal in Kubeflow 27.03. Pipelines now supports garbage collection for both S3 artifacts and the database.
  • Kubeflow Trainer 2.4.0 adds the OptimizationJob API (alpha), the planned successor to Katib Experiments which is now deprecated , alongside TrainJob improvements for workload-aware scheduling and DRA.
  • Istio 1.31.3, Knative Serving and Eventing 1.24.0, cert-manager 1.21.2, Dex 2.46.1 and OAuth2-Proxy 7.15.5. Knative Eventing remains optional.
  • Interactive Spark Connect integration tests from a Kubeflow Workspace, improved component diagnostics, and security scanning migrated from Trivy to OSV-Scanner.

Kubeflow Community Distribution:

  • Documentation updates that make it easier to install, extend and upgrade Kubeflow.

Pipelines

🚀 Features

Kubeflow Pipelines introduces capabilities centered on automatic artifact previews, pipeline visualization, data management, and automated quality workflows:

  • Automatic artifact previews: Supported Python components can generate Dataset and Model previews in run details, helping you inspect outputs without downloading the full artifact. #15087
  • Clearer pipeline visualization: Nested sub-DAGs expand inline in the UI. Standalone HTML/Mermaid previews with local watch mode let you explore pipelines without deploying a server. #14864, #15064
  • More authoring options: Components gain Kubernetes Dynamic Resource Allocation, init containers, Pydantic BaseModel inputs and outputs, and custom task cache keys. DRA requires a compatible backend, Kubernetes configuration, and resource driver. #14243, #13651, #13995, #13762
  • Pipeline data management: Export/import transfers experiments, pipeline versions and tags, completed run history with MLMD lineage, and schedule definitions between compatible installations. Optional retention policies archive and delete expired completed runs; retention is disabled by default. #14659, #13532
  • GitHub Agentic Workflows (gh-aw): Introduced automated issue triage and quality verification workflows using GitHub Agentic Workflows (gh-aw) to streamline review cycles, maintain contribution quality, and support maintainer velocity. . #13293, #14022, #14109, #14035

Trainer

This release, Kubeflow Trainer focused on scheduling, observability and monitoring through Workload-Aware Scheduling and Dynamic Resource Allocation. It also introduces the OptimizationJob API (alpha), which replaces Katib. Katib is now deprecated; v0.19.0 still ships in 26.10 to give users time to migrate.

Check out Kubeflow Trainer v2.4 blog post to learn more about these features.

🚀 Features

Workload-Aware Scheduling

This feature introduced integrating the Kubernetes Workload API into Kubeflow Trainer to enable native workload aware scheduling for TrainJobs. The Workload API, introduced in Kubernetes v1.35 (alpha) and promoted to beta in Kubernetes v1.37, provides multiple features to enhance AI workload scheduling orchestration including:

  • gang-scheduling: KEP-4671,
  • topology-aware scheduling: KEP-5732,
  • DRA: KEP-5729, and other features through the Workload and PodGroup resources.

OptimizationJob API

Implement the full API schema for OptimizationJob, CEL and Webhook validation rules. Moving from Katib legacy Experiment CRD to OptimizationJob CRD.

By integrating OptimizationJob natively under the trainer.kubeflow.org API group, we unify the user experience and enable shared observability with TrainJobs.

Key features of this API schema: CEL-Native Validation, Declarative HPO, Manifests & Tooling.

Dynamic Resource Allocation

Dynamic Resource Allocation (DRA) graduated to GA in Kubernetes 1.34, providing a modern alternative to extended resources for GPUs and accelerators. This KEP adds a top-level resourceClaimsPerNode field on Trainer, next to resourcesPerNode, so data scientists can request DRA devices with the same UX they already use for CPU/memory/GPU counts. The controller applies these claims to the trainer node PodSpec and wires container-level resources.claims on the node container. Claims for other containers (sidecars, init containers) are configured via the runtimePatches API. It also updates GPU auto-detection so numProcPerNode continues to work with DRA.

Here’s the KEP for this feature:

  • KEP-2782: Dynamic Resource Allocation support for TrainJob #3540

Scheduling & Integrations:

  • Allow users to select a scheduler per TrainJob through the existing RuntimePatches API, without duplicating or modifying a shared TrainingRuntime. #4265

  • JobSet previously supported multi-slice TPU with replica corresponds to the number of slices parallelism corresponds to the number of hosts in a single slice. There should be an easy to use way to specify these params for multi-TPU training jobs. #4250

  • We introduced a new ComponentDeleterPlugin interface in Kubeflow Trainer to automatically delete Volcano PodGroup resources when a TrainJob enters a Failed, Complete, or suspended state.

  • Previously, PodGroup objects remained in the cluster and permanently held onto minResources in the Volcano queue, blocking other jobs from running.

  • The update also prevents the Volcano plugin from recreating the PodGroup while a job is suspended avoiding a create-delete loop and ensures a fresh PodGroup is built cleanly upon resumption. Additionally, it adds the required RBAC delete permissions for Volcano PodGroup resources and updates the Makefile to properly fetch the Volcano CRD for integration tests. #4059

  • An opt-in Prometheus monitoring support for the Kubeflow Trainer controller by enabling metric scraping via Prometheus Operator. Key changes include Kustomize & Helm Integration, Security & Authentication, RBAC Parity, Scope focuses strictly on making existing controller-runtime metrics scrapeable rather than introducing new Trainer-specific metrics. #4102

  • The Katib project is deprecated. Users should migrate to the OptimizationJob APIs, which are released as part of the Kubeflow Trainer project under the alpha feature gate.

OptimizationJob is the next step for hyperparameter optimization in Kubeflow. It is natively integrated with the TrainJob API, so every trial can use Trainer runtimes and distributed training features out of the box. Metrics are pushed through the Kubeflow SDK and Trainer status server, so you no longer need a separate database or a metrics collector sidecar.

Work on the remaining features is tracked in Issue-3562.

  • We added operator documentation for scheduling TrainJob workloads using slurm-bridge on hybrid Kubernetes and Slurm clusters. Key highlights include: New Operator Guide, Scheduler Integration Scope, Setup & Usage Details #3951

Spark Operator

Kubeflow 26.10 ships Spark Operator 2.5.2 (up from 2.5.0 in 26.03):

  • Spark 4.0.4 base image. #3061

  • Kustomize as a first-class install path, with a Prometheus PodMonitor, PodDisruptionBudget, and drift detection that keeps Helm and Kustomize in sync. #2919, #2922, #2918, #2933

  • Safer defaults: least-privilege controller RBAC and webhook validation of sparkConf keys. #2914, #3043

  • Observability and scale: a new spark_application_submit_latency_seconds metric and --kube-api-qps / --kube-api-burst controller flags. #2942, #2865

  • Spark Connect fix: the BlockManager port now matches the Service definition. #2948

Our bi-weekly community call is now called “Spark on Kubernetes” (Fridays, 9:00 AM PST).

    • Static LoRA Adapter Support

The KServe UI is a component of KServe that provides a user-friendly way to handle the lifecycle of InferenceService CRs in a Kubeflow cluster. This allows users to create, delete, and inspect the state of their Model Servers without needing to interact with Kubernetes resources directly.

What’s New

Kubeflow Distribution Committee

As Kubeflow has graduated to a CNCF project and as it expands across enterprise platforms and hybrid environments, ensuring consistency, reliability, and smooth integration across individual subprojects has become critical. To address this, we are introducing the Kubeflow Distribution Committee (KDC), a vendor-neutral governance body dedicated to maintaining a robust and production-ready ecosystem.

While the primary focus of the KDC is to empower the Kubeflow Subprojects as modular, high-quality components, the Kubeflow Community Distribution (KCD) serves as a primary example of this effort – providing a validated community-supported implementation that demonstrates the collective power of these projects in a unified platform. The committee will only approve policies and decisions that support the following goals:

  • Promote the Kubeflow community’s vision, values, and mission in collaboration with the KSC, KOC, and WG Chairs.
  • Validate, report on, and advocate for the consumability of Kubeflow Subprojects by defining requirements for portability and ease of deployment across heterogeneous environments. This includes identifying integration-gaps such as unexposed configurations or packaging hurdles—and opening issues with maintainers to help prioritize improvements necessary for the Kubeflow Subprojects to be effectively integrated into the KCD and the broader vendor ecosystem.
  • Define and maintain the requirements for external projects and distributions of Kubeflow Subprojects to be eligible to use the Kubeflow Conformant mark.
  • Define and maintain the requirements for the Kubeflow Community Distribution. Subject to the KCD Decision Process.

Semantic Operator

A Kubernetes operator and server that runs an Apache Ossie semantic layer on your existing data platform. You define each business metric once, in a SemanticModel resource. A deterministic compiler turns every request into exactly one governed SQL statement, so AI agents (over MCP), apps (over REST), and BI tools (over SQL views) all compute the metric the same way. The LLM only selects certified metrics and dimensions. It never writes SQL.

Here’s our architecture:

Many AI agents ask an LLM to generate SQL directly from a warehouse schema. The SQL can run successfully while using the wrong business definition. We measured both approaches across 30 business questions, with three phrasings each at temperature 0:

Path Accuracy Consistency across phrasings Wrong answers
Raw text-to-SQL 62/90 (69%) 19/30 (63%) 28
Semantic Layer 87/90 (97%) 27/30 (90%) 3

Every raw-path miss executed without error and returned a confidently wrong number. Full results and method → https://kubeflow.github.io/semantic-operator/examples/benchmark-results/

  • Check out the blog: https://blog.kubeflow.org/introducing-semantic-operator/

Kubeflow Docs Agent

Meet our Project FLO!

Who FLO is?

FLO is an agentic RAG (Retrieval-Augmented Generation) documentation assistant built to power the Kubeflow website. Developed within the kubeflow/docs-agent repository by open-source maintainers including Santhosh_t and Rohit Kumar (who heavily developed the “FLO” persona during a Google Summer of Code 2026 project), it serves as the official LLM-powered assistant for the community. FLO aligns directly with the architectural goals of the Kubeflow Agents Working Group (WG-Agents), serving as a practical implementation of autonomous agentic workflows and Model Context Protocol (MCP) server integrations on Kubernetes. Rather than relying on standard text search, FLO uses these MCP toolsets and hybrid retrieval (combining dense vector embeddings with BM25 sparse retrieval via a Milvus vector database) to pull context from across the entire Kubeflow surface—including prose documentation, GitHub issues, source code, and deployment manifests.

Key technical capabilities of the FLO agent include:

  • Production GitOps & Evals: The agent is managed and deployed using Argo CD GitOps workflows. When changes are merged to the docs-agent repository, a staging step runs an LLM-as-a-judge evaluation dataset (logging telemetry to Langfuse) so that every update is scored for quality before reaching production.
  • Automated Issue Triage: Beyond answering website queries, FLO’s underlying retrieval engine is equipped with instruction and label sets to automatically triage new GitHub issues based on its documentation grounding.
  • Cloud-Native Serving: Operating entirely within Kubernetes environments, it utilizes models like Llama 3.1 or Gemma and leverages KServe inference services with WebSocket and HTTP streaming for real-time, bidirectional communication with users.

Kubeflow users often struggle to find relevant information across the extensive documentation scattered across different services, components, and repositories. The traditional search approach lacks context and often returns irrelevant results. This documentation assistant addresses these challenges by:

  • Semantic Search: Understanding the intent behind queries rather than just keyword matching
  • Contextual Responses: Providing answers based on the most relevant documentation chunks
  • Real-time Processing: Enabling instant responses through streaming APIs
  • Scalable Architecture: Leveraging Kubernetes for automatic scaling and resource management

Check out the project here: https://github.com/kubeflow/docs-agent
